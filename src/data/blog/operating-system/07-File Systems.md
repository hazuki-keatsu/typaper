## 6.1 文件

### 长时信息存储
- 三大需求：
  - 存储大量信息
  - 进程结束后信息依然存在
  - 多进程并发访问
- 解决方案：将信息存储在磁盘等外部介质上，以**文件**为单位。

### 文件命名
- 不同系统命名规则不同（大小写敏感、长度限制等）
  - 在Unix系统上，区分大小写；而MS-DOS上，不作区分。

- 常见两段式文件名（如 `prog.c`），点号后为**文件扩展名**

### 文件结构
- 三种结构：
  - 字节序列（a）（UNIX、Windows）：文件被看作一个无结构的字节流，操作系统不关心文件内部的内容格式，所有解释工作由应用程序完成。
  - 记录序列（b）（如80字符卡片）：文件由一组固定长度或可变长度的记录（record）组成，操作系统提供对记录的读取、写入和定位操作。
  - 树形结构（c）（大型机商业数据处理）：文件内部组织成树形结构，节点包含键值字段，支持按关键字快速检索。

![image-20260520210845210](/images/operating-system/image-20260520210845210.png)

### 文件类型
- 按用途：系统文件、用户文件、库文件
- 按数据格式：源文件、目标文件、可执行文件
- 按访问控制：只执行、只读、读写
- 按逻辑结构：结构化、非结构化
- 按物理结构：顺序、链接、索引
- UNIX/Windows 还有：
  - 普通文件（ASCII 或 二进制）：容纳用户信息
  - 目录：用来维护文件系统结构的系统文件
  - 字符/块特殊文件：用于模型磁盘，一种用于**存储和分发系统镜像、虚拟机模型**的虚拟磁盘文件

### 文件访问
- **顺序访问**：从头到尾，可回退（适用于磁带）
- **随机访问**：任意顺序读写（适用于数据库）

### 文件操作
创建、删除、打开、关闭、读、写、追加、定位（seek）、获取/设置属性、重命名

### 内存映射文件
将文件映射到进程地址空间，便于直接访问。

## 6.3 文件系统实现

### 文件系统布局
- 文件系统存储在磁盘上。
- 大多数的磁盘可以划分为一个或者多个分区，每个分区上有独立的文件系统。

> 磁盘的第0扇区称为MBR（主引导记录），用于启动计算机。

![image-20260521092811177](/images/operating-system/image-20260521092811177.png)

- 分区表：给出每个分区的开始和结束的地址
- 启动块：放置着文件系统启动分区
- 超级块：魔数、块的数量等等
- 空闲空间管理：以位图或者指针列表的形式存在的空闲块
- i节点：一个数据结构数组，每个文件存在一个

### 文件的实现

文件实现的核心问题是：**如何在磁盘上记录各个文件分别使用了哪些磁盘块**。不同的系统有不同的实现方式：

#### 连续分配

![image-20260521093351196](/images/operating-system/image-20260521093351196.png)

**原理**：将每个文件作为一连串连续的数据块存储在磁盘上。目录项只需记录文件的起始块号和块数。

**优点**：
- 实现极其简单，目录项只存两个数字；
- **读取性能高效**，整个文件在磁盘上物理连续，一次寻道即可顺序读完。

**缺点**：
- **外部碎片**：经过反复创建和删除文件后，磁盘上散布着大量小块空闲空间，总和够用但每一块都不够大，导致无法分配；
- **增长困难**：创建文件时需要预先知道文件最终大小。如果文件要增长而后面紧挨着另一个文件，要么移动整个文件到更大的空闲区域（开销大），要么无法增长。

连续分配常用于 **CD-ROM 文件系统**，因为光盘上的文件大小在刻录时就确定不变，不存在后续增长和碎片问题。

#### 链表分配

![image-20260521093704323](/images/operating-system/image-20260521093704323.png)

**原理**：文件不是连续存放的，而是将各个数据块串联成一条链表。每个数据块在末尾留出一定字节作为指针，指向下一个数据块的磁盘地址。目录项只需要存储第一个块的地址，然后顺着指针就能遍历整个文件。

**优点**：
- **没有外部碎片**，任何空闲块都可以被利用；
- 文件大小不必在创建时确定，**动态增长很自然**，只需从空闲列表中取一个新块，挂到链表末尾即可。

**缺点**：
- **随机访问极其慢**，要读第 1000 个块，必须先顺序遍历前 999 个块，即需要 999 次磁盘 I/O；
- 每个块末尾的指针会占用原本的数据空间，导致每个块存储的用户数据不是 2 的幂次方，对于按块缓存的程序来说不太方便；
- 如果链表中某个指针损坏，整个文件从损坏点开始全部丢失。

#### 文件分配表 (FAT) —— 存储在内存中的链表

<img src="/images/operating-system/image-20260521093934129.png" alt="image-20260521093934129" style="zoom:50%;" />

**原理**：将链表指针从数据块内部"抽出来"集中放在一个单独的表中，这个表就是 **FAT（File Allocation Table，文件分配表）**。FAT 存放在内存中，由磁盘上每个块对应一个表项。目录项仍然只存首块号，通过查找 FAT 即可在内存中跟随链表，不必每次访问磁盘数据块上的指针。

**优点**：
- 保留了链表分配灵活增长、无外部碎片的优点；
- **随机访问大幅改善**——跟随链表的操作全部在内存中进行，只需找到目标块号后再去磁盘读一次数据。

**缺点**：
- **FAT 表必须始终驻留在内存中**。对于大磁盘，FAT 表本身就会占用大量内存。

FAT 在历史上有重要应用：**MS-DOS** 和早期的 **Windows**（包括 Windows 98）都使用 FAT-16 / FAT-32 文件系统。U 盘和 SD 卡至今仍常格式化为 FAT32 以保持跨平台兼容。

#### i-node（索引节点）

为每个文件关联一个称为 **i-node（index-node，索引节点）** 的数据结构，该结构列出文件块的属性和磁盘地址。目录中只保存文件名和对应的 i-node 编号，文件的所有元数据和块地址表都集中存储在 i-node 中。

<img src="/images/operating-system/image-20260521094507561.png" alt="image-20260521094507561" style="zoom:50%;" />

**i-node 结构**（以 UNIX V7 为例，共 15 个地址指针）：
- **前 12 个指针**：直接指向数据块（直接块），适合小文件；
- **第 13 个指针**：指向一个间接块，该块再包含若干数据块指针（一级间接）；
- **第 14 个指针**：指向一个二级间接块（指针的指针的指针）；
- **第 15 个指针**：指向一个三级间接块。

**为什么这样设计？** 大多数文件都很小（研究发现约 80% 的 UNIX 文件小于 10KB），12 个直接块就足以覆盖绝大多数情况。而大文件通过间接块也能访问到极大的磁盘空间。这种"越大的文件越慢一点"的不对称设计，恰恰与实际使用分布相符。

**优点**：
- i-node **只在对应文件打开时才需要加载到内存**——没有打开的文件其 i-node 留在磁盘上，不占用内存。这与 FAT 的"全表常驻内存"形成鲜明对比，是 UNIX 类系统可支持超大文件系统的重要原因。

**四种实现方式对比总结**：

| 方式     | 无外部碎片 | 随机访问 | 内存开销     | 代表系统     |
| -------- | ---------- | -------- | ------------ | ------------ |
| 连续分配 | ✗          | ✓ 极快    | 极低         | CD-ROM       |
| 链表分配 | ✓          | ✗ 极慢    | 极低         | TOPS-10      |
| FAT      | ✓          | ✓ 快      | 高（全表常驻） | MS-DOS, USB  |
| i-node   | ✓          | ✓ 快      | 低（按需加载） | UNIX, Linux  |

### 目录的实现
- 目录项存放属性的两种方式：
  - 直接存放在目录项中（Windows）
  - 存放在i-node中（UNIX）
- **长文件名处理**：
  - **限制长度**：最简单粗暴的做法，直接规定文件名最大长度（如 MS-DOS 的 8.3 格式，文件名最多 8 字符 + 扩展名最多 3 字符）。优点是实现极其简单，目录项大小固定，查找和遍历效率高。缺点是如果用户起了一个短名（如 `a.c`），目录项中预留的空间就浪费了；而真正需要长名时又放不下。
  - **变长目录项**：每个目录项的长度随文件名实际长度而变化（在目录项头部记录本条目长度）。优点是不浪费空间，支持任意长度文件名。缺点是删除一个文件后留下的空隙可能和后续新文件的文件名长度不匹配，导致目录中产生碎片化的间隙，需要定期压缩整理。
  - **固定目录项 + 堆存放文件名**：目录项本身大小固定（查找效率高），但文件名不直接存放在目录项中，而是将所有文件名集中存放在目录末尾的一个"堆"区域，目录项只存一个指向堆中文件名位置的指针。优点是兼顾了查找效率和灵活性，没有内部碎片。缺点是实现复杂度稍高，需要管理堆空间。

> **现实中的做法**：Windows 98 采用的是"多目录项串联"的方法——长文件名用多个连续的目录项来存储（每个目录项存一段），同时在最后附带一个兼容 MS-DOS 的 8.3 短名目录项。UNIX 则采用"固定目录项 + i-node 引用"的方式，目录项只存文件名和 i-node 号，真正的元数据在 i-node 中。

![image-20260521094941845](/images/operating-system/image-20260521094941845.png)

### 共享文件

同一个文件可能被多个用户或进程使用，文件系统需要提供"共享"机制，即让同一份物理数据在文件系统树中出现于多个位置。主要有两种实现方式：

#### 硬链接

**原理**：硬链接本质上就是多个目录项指向**同一个 i-node**。每个 i-node 内部维护一个**链接计数**，记录有多少个目录项指向自己。创建硬链接时（如 `ln fileA fileB`），系统新建一个目录项 `fileB`，指向与 `fileA` 相同的 i-node，并将该 i-node 的链接计数 +1。

实例——执行 `ln /usr/jim/memo /usr/ast/note` 后：

```
/usr/jim/memo ──┐
                ├──► i-node #123 (链接计数 = 2) ──► 数据块
/usr/ast/note ──┘
```

两个文件名地位完全平等，不存在"谁是原文件谁是副本"的区别——它们就是同一个文件的两个名字。

**优点**：共享文件只占用一份数据块，后续修改在任何路径上打开都能看到一致的内容，空间效率高。

**缺点与问题**：
- **删除问题 / 悬空指针**：如果用户 `jim` 执行 `rm /usr/jim/memo`，系统只删除该目录项，将 i-node 链接计数减 1（从 2 → 1）。此时数据块仍然存在，文件通过 `/usr/ast/note` 仍可正常访问。只有当链接计数减到 0 时，系统才真正释放 i-node 和数据块。但如果实现不当（如删除目录项后立即释放 i-node 而不管引用计数），就会出现**悬空指针**——其他目录项指向一个已不存在的 i-node。
- **不能跨文件系统**：因为 i-node 号只在同一个文件系统内有效，硬链接不能跨越不同的分区或文件系统。
- **不能链接目录**：多数 UNIX 系统禁止对目录创建硬链接（root 除外），因为目录之间的硬链接可能形成环，导致 `find` 等工具陷入死循环。文件系统树本应是有向无环图（DAG）结构。

#### 符号链接

**原理**：符号链接（又称软链接，symbolic link / soft link）并不直接指向 i-node，而是创建一个**类型为"符号链接"的小文件**，其数据内容就是目标文件的**路径名**。创建方式如 `ln -s /usr/jim/memo /usr/ast/note`。

实例：

```
/usr/ast/note ──► [符号链接文件] ──内容为"/usr/jim/memo"──► 路径解析器查找 ──► i-node #123 ──► 数据块
```

符号链接实际存储的是字符串 `"/usr/jim/memo"`，每次访问时系统会先读取这个路径，然后按路径找到真正的目标文件。

**优点**：
- **灵活性极高**——可以链接任何东西，包括目录、跨文件系统的文件，甚至不存在的文件。后者称为"断符号链接"（dangling symlink），虽然不可用但不报错，创建时不需要目标文件已经存在。
- **不受文件系统边界限制**，目录项存储的是路径字符串，不依赖 i-node 号跨分区有效。

**缺点**：
- **额外的 I/O 开销**——每次访问符号链接指向的文件，系统需要先读一次符号链接文件本身来获取路径字符串，再根据路径去查找真正的目标文件，至少多一次磁盘访问。
- **空间开销**——符号链接自身是一个独立的小文件，需要占用一个 i-node 和一个（通常一个）数据块来存储路径字符串。

#### 两种链接方式下目录遍历的重复问题

当目录中存在链接时，如果用常规的递归遍历算法（如 `find`、`tar`、`cp -r`），可能会遇到同一个物理文件被定位多次的问题：

- **硬链接**：同一个 i-node 对应多个路径，遍历时如果在两个目录中都发现了指向同一 i-node 的文件，不加判断的话就会对同一份数据重复备份、重复打包。
- **符号链接**：链接可能指向目录，目录内部可能又有符号链接指回上级目录或其他路径，形成**循环**，导致遍历程序无限递归。

解决方案通常是在遍历过程中**记录已访问过的 i-node 号**（对硬链接）/ **已访问过的路径**（对符号链接），遇到重复则跳过。常见工具中：`tar` 默认不解引用符号链接（只打包链接本身），`ls -l` 显示链接计数可以帮助识别硬链接。

### 盘空间管理
- **块大小**：影响数据速率和空间效率（2-KB是常见的选择）

  ![image-20260521112712489](/images/operating-system/image-20260521112712489.png)

- **空闲块管理**：

  - 链表方式
  - 位图（更节省空间）

  ![image-20260521112848554](/images/operating-system/image-20260521112848554.png)

- **磁盘配额**：多用户系统中，防止单个用户占用过多磁盘空间的机制。系统管理员为每个用户（或用户组）设定两个上限：
  
  - **软限制**：允许用户在一段时间内超过的限额，超限时会收到警告，但不会立即被阻止写入；宽限期过后仍超限，软限制将变为硬限制。
  - **硬限制**：用户绝对不能超过的绝对上限，一旦触及，任何新的写入操作都会被拒绝。
  
  配额信息通常记录在每个用户的配额文件中，系统在每次进行磁盘块分配和释放时更新用户的已用块数和已用 i-node 数。当用户写入文件时，内核检查"当前使用量 + 本次分配量"是否超过限额，若超过则拒绝写入并返回错误（如 `EDQUOT`）。磁盘配额在分时系统（如大学共享服务器、企业文件服务器）中尤其重要，确保磁盘资源在多个用户之间公平分配。

### 文件系统可靠性

- 备份是很重要的
  - 通常更倾向于只备份特定的 dir 及其中的所有内容，而不是整个文件系统。
  - **增量转储**：指仅备份或转移自上次操作后发生变化的数据，而非全部数据。
  - 在写入磁带前压缩数据可能更理想，但备份磁带上的一个缺陷点可能破坏解压算法，使整个文件无法读取。
  - 在活跃文件系统上执行备份是困难的。 通过复制关键数据结构，快速快照文件系统状态。
  - 备份磁带应存放在场外。
- 两种方法用来将磁盘转储到磁带上
  - 物理转储：从磁盘的第0块开始，将所有磁盘块按顺序写入输出磁带，复制完最后一个块后停止。**优点**：简单快捷；**缺点**：无法跳过选定的目录、进行增量转储，以及根据请求恢复单个文件。
  - 逻辑转储：从一个或多个指定的 dir 开始，递归地转储所有自某个基数据以来发生变化的文件和 dir。

- 棘手之处：
  - 由于空闲块列表不是文件，因此不会被转储，因此在所有转储恢复后必须从头重建。
  - 如果文件链接到两个或更多 dir，文件只恢复一次非常重要。
  - UNIX 文件可能包含漏洞。中间的块不属于文件，不应被倾倒或恢复。
  - 特殊文件、命名文件等绝不应被转储。

### 文件系统一致性
如果系统在所有修改块写入前崩溃，文件系统可能会处于不一致状态。

### 文件系统性能
- **缓存**：使用LRU等策略，sync系统调用定期刷新
- **预读**：顺序读取时提前加载
- **减少磁臂移动**：
  - 通过将可能按顺序访问的方块彼此靠近放置，这样在位图记录中很容易选择。
  - 即使是空闲列表，也可以做一些块聚类。
  - 对于i节点系统，即使是读取一个短文件也需要两次磁盘访问。一个代表i节点，一个代表块。
    - i 节点通常位于磁盘的开头附近。
    - 把 i 节点放在磁盘中间。
    - 将磁盘划分为柱面组，每个柱体组有自己的i节点、块和自由列表。

### 日志结构文件系统 (Log-Structured File Systems，LFS)
CPU更快，内存更大，磁盘缓存也可以更大。越来越多的读取请求可以直接来自文件系统缓存，无需磁盘访问。因此，大多数磁盘访问都是写入的

LFS 策略是将整个磁盘结构化为日志，所有写入初始缓冲在内存中，定期将这些写入磁盘日志末尾。打开文件时，使用表定位i节点，然后查找块。

LFS有更干净的线程，会花时间环绕扫描日志以压缩。

### Linux 文件系统
- **EXT2**：
  - superblock：记录文件系统的整体信息，包括i node/block的总量、使用量、剩余量，以及文件系统的格式与相关信息等
  - i node：记录文件的属性，一个文件占用一个i node，同时记录此文件的数据所在的 block 编号
  - block：实际记录文件的内容，若文件太大时，会占用多个 block。EXT2支持1K、2K和4K的block大小。
- **EXT3**：增加日志功能，支持大目录索引
- **EXT4**：
  - 兼容EXT3
  - 支持更大的系统和更大的文件，EXT4 分别支持 1EB（1,048,576TB）的文件系统，以及 16TB 的文件
  - 无限数量的子目录
  - 支持extents，每个 extent 为一组连续的数据块
  - 支持多块分配，支持一次调用分配多个数据块
  - 延迟分配，现代文件系统都尽可能地延迟分配，直到文件在 cache 中写完才开始分配数据块并写入磁盘
  - 快速fsck，EXT4的快速fsck利用日志回放和延迟检查机制，仅验证关键元数据而非全盘扫描，从而在几秒内完成一致性修复。
  - 日志校验
  - 无日志模式
- **XFS**：
  - 支持超大文件和文件系统，特别擅长处理大文件
  - 分配组
  - 支持条带化
  - 支持extents
  - 可变块尺寸
  - 延迟分配
  - 稀疏文件
  - 原生备份/恢复工具
- **VFS（虚拟文件系统）**：统一接口管理多种文件系统。使用者并不需要知道每个分区的文件系统是什么，向上提供统一的文件系统接口。
